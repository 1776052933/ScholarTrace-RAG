# 单用户入库流水处理与验收（2026-11-03）

## 改动范围

选中多篇论文后，入库任务一次提交全部待下载论文，复用下载器已有的最多 3 个网络线程。下载器在 worker 主线程顺序提交 MySQL 状态。若批次准备整体报错，逐篇准备以隔离故障。

已下载的论文依次进入解析与索引。一个预解析线程提前处理下一篇 PDF；主线程对当前论文生成 Embedding、写入 Milvus，并回写 MySQL。任一时刻最多一个解析任务和一个索引写入任务，预解析队列只提前一篇。单篇失败保留独立状态与重试；取消时未完成论文回到待处理状态。

本轮没有提高 Celery worker 进程数，也没有并行执行 BGE-M3 推理或 Milvus 写入；仍面向一名本机用户。

## 验收

- 代码回归：`test_m1_rag.py`、`test_m4_async.py`、`tests/papers/test_parallel_downloads.py`、`test_paper_library_api.py` 共 **26 通过**。覆盖批次下载、预解析与索引重叠、解析失败隔离、重试、取消和已有文档功能。
- 真实 Compose 环境复用此前隔离的数据库与向量库，使用相同的两篇本地公开 PDF，Docling、CPU BGE-M3 和 Milvus 入库；无第三方模型 API 调用。未开启解析预取的本轮对照为 **183.59 秒**；开启后为 **168.70 秒**，本次减少 **14.89 秒（约 8.1%）**。
- 两轮入库均完成，每篇各尝试一次。优化后 MySQL 完成状态与 Milvus 片段数量一致：Attention 158、Dexterous Review 287。新索引检索到 Transformer 表格的 `28.4` 和 `41.8`；此前已入库的两篇测试论文向量数量仍为 158 和 287。
- 日志显示第二篇在第一篇尚未完成索引时开始解析。流水处理期间对 worker 的一次抽样为约 4 核 CPU、2.94 GiB 内存，占用并非全过程峰值。

这组耗时只反映两篇固定 PDF 在本机的一次配对验收，受模型缓存、系统负载和 Milvus 状态影响；不能推断所有论文或网络下载的固定加速比。因为 PDF 已在本地，下载并发在这组耗时里基本没有发挥作用。问答生成没有重跑，原有模型回答质量不能据此判断。

本机原始入库记录保存在 `data/repro_acceptance_20261102/runtime/concurrency_acceptance_20261103.json` 和 `concurrency_acceptance_20261103-b.json`；这些测试数据被 Git 忽略。验收后停止 Compose 容器，保留数据卷。
