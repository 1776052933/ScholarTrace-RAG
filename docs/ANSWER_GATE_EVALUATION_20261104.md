# 回答支持性门控的首轮真实模型评测（2026-11-04）

## 评测口径

这次固定旧 M3 的 22 道 PDF 问题、两种解析方式产生的 44 条缓存 DeepSeek 回答及其引用摘录，直接把**同一条旧回答**交给当前正式使用的 `strict_gate` 和 DeepSeek 核验提示词。使用用户已填写的 44 条“回答正确 / 引用支持”判断作对照；人工复核有中文翻译辅助，尚非第二名独立审核者复核。所有 22 道问题在原 PDF 中都有可核对答案。

此设计只隔离评估**新增拒答门控**：不重跑 PDF 解析、向量检索或生成答案，也不等同于当前 API 的 44 题完整能力。旧记录保存的是引用摘录，正式链路使用当前检索到的完整 chunk；若摘录被截断，两者核验输入可能不同，因此 82.5% 不能直接当成正式系统误拒率。旧缓存答案于 2026-10-17 生成，本次核验于 2026-11-04 进行；模型服务版本和运行环境可能不同。旧人工复核表未被修改。

为补足 44 条里没有“具体错答”的缺口，又基于既有引用摘录手工构造 10 个控制/反例：两篇论文各自数字、交换两篇归属、跨论文过度概括、表格行列混淆、证据中没有的事实、缺少一篇引用与虚构引用。它们**不是模型自然生成的错误答案**，单独统计。

最后在隔离 Compose 环境、真实 MySQL/Milvus/DeepSeek API 下对既有两篇公开 PDF 跑 3 道完整 API 小样本；严格门控打开和关闭各一次。两轮都用当前代码与同一索引，但生成调用不共享同一输出，所以仅用于流程和失败原因检查，不计算质量提升率。

## 44 条固定旧答案的配对结果

| 指标 | 原缓存回答 | 同一回答经过新门控 |
| --- | ---: | ---: |
| 用户判定正确 | 40/44 | 放行 7 条正确回答 |
| 用户判定错误 | 4/44 | 4 条旧拒答继续拒答 |
| 用户判定引用支持 | 40/44 | 放行的 7 条均被判支持 |
| 原本正确却被拒绝 | 不适用 | **33/40（82.5%）** |
| 有事实内容的人工已判错答案被放行 | 此集合没有这种样本 | 无法估计 |

4 条旧错误全部是“PDF 有答案、原检索片段没有、旧系统拒答”，并非具体事实答错。故“放行的 7 条都正确”**不能**证明误答率为零，也不能证明新门控减少了真实误答。

40 条需要模型核验，全部完成；输入 27,303 token、输出 2,610 token；核验调用耗时合计 218.56 秒，单次 P50 5.43 秒、P95 约 5.86 秒。这是核验阶段耗时，不是完整问答延迟。44 条拒答/放行原因：`verified_support` 7、`model_abstained` 4、`unquoted_number` 29、`unsupported` 1、`uncertain` 1、`quote_not_verbatim` 1、`missing_source_quote` 1。

**主要失败模式：**数字规则对回答中所有阿拉伯数字做逐字匹配。核验器可能只摘出表格数据行，未摘“Table 3”标题，于是正确的 `25.8` 答案因数字 `3` 不在引句中被拒。其他样本中的年份、引用 ID、百分号格式也出现类似问题。`unquoted_number` 29 条并不代表 29 条答案数字错误；其中绝大多数为用户判定正确的回答。当前规则过度拒答，不能将它作为问答质量提升对外宣传。

## 构造反例与当前 API 小样本

10 个构造样本中，两个应放行的控制样本均放行，八个应拒答样本均拒答；7 次实际模型核验、3 次程序前置拦截。模型核验输入 7,039 token、输出 168 token，耗时合计 37.48 秒。结果说明已设定的错列、错行、交换论文归属等反例在此批被拦截；样本少且经过手工设计，不能外推自然错答检出率。

完整 API 的三道题（同一索引、当前代码；两次独立生成）：

| 问题 | 严格门控 | 门控关闭时 |
| --- | --- | --- |
| 单论文：Transformer 编码器层数 | 正确回答 6 层，1 个引用 | 同样回答 6 层，1 个引用 |
| 多论文：分别回答编码器层数及价值型 RL 采样优点 | 无引用拒答 | 只引用第二篇；承认第一篇片段未给出层数，给出第二篇的部分事实 |
| 多论文：是否同数据集报告 F1 | 无引用拒答 | 引用片段并说明无法确定 |

多论文复合问题的旧式回答显示第一篇关键证据没有进入上下文；严格模式拒绝完整结论有依据，但未解决检索缺证据。第一题严格模式的 17.71 秒与关闭门控的 10.87 秒受到容器重启、首次嵌入模型加载和不同生成输出影响，**不能**作为门控净延迟对照。后两题也只是流程样本。

## 调用、费用与可复核文件

上述两个离线试验合计 47 次直接 DeepSeek 核验调用，输入 34,342 token（其中缓存命中 3,456、未命中 30,886）、输出 2,778 token；不包括 6 次 API 小样本的生成/核验 token。调用时配置的模型名是旧别名 `deepseek-chat`，而 [DeepSeek 当前公开价目表](https://api-docs.deepseek.com/quick_start/pricing/)只列出 `deepseek-flash` 和 `deepseek-v4-pro`。若**仅假设**这 47 次按当时非高峰 Flash 价格计费，依据 API 返回的缓存命中/未命中 token 估算约 0.0063 美元；这不是实际账单，旧别名的实际映射及 6 次 API 小样本费用未核实。

可复跑入口：

- `python -m evaluation.strict_gate_review_eval`：44 条配对核验；仅缺少的记录才会调用模型。
- `python -m evaluation.strict_gate_adversarial_eval`：10 个构造反例。
- `python -m evaluation.current_rag_smoke_20261104`：隔离 API 的 3 个小样本，需先启动对应服务。

逐题原始结果与汇总位于被 Git 忽略的 `evaluation/runs/strict_gate_review_20261104/`、`evaluation/runs/strict_gate_adversarial_20261104/`、`evaluation/runs/current_rag_smoke_20261104/` 和 `evaluation/runs/current_rag_smoke_no_gate_20261104/`。每条保存模型原始核验 JSON、决策、耗时与 token；不保存 API 密钥。脚本已通过 Python 语法编译检查。

## 结论

**当前严格门控不满足“尽量减少误答，同时保留可回答题”的目标。**先修复表号、年份、引用 ID 等非答案数值触发的错误拒答，再用这 44 条固定答案重测；同时补充真正由模型自然产生、经 PDF 人工判错的答案，才能估计错误放行率。多论文复合问题还需要另测逐篇证据命中，不能把检索漏证据与门控误拒混为一谈。新规则必须在未参与调参的 PDF 问题上再次验证。
